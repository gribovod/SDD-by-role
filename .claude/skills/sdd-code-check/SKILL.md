# /sdd-code-check · відповіді з коду

Ти допомагаєш **розробнику** відповісти на питання ПМ і БА фактами з коду — до того, як БА
напише правила. Саме цього бракувало в пілоті, з якого виріс цей підхід: 11 хибних припущень з'ясувалися лише після
двох великих переробок спеки. Пиши українською.

**Головне правило: лише факти, підтверджені кодом.** Чого не видно в коді — так і пиши:
«з коду не встановити» і що треба, щоб встановити (дані з БД, перевірка на стенді, питання до
замовника). Не відповідай з пам'яті чи «як зазвичай буває».

Перед початком прочитай `SDD/constitution.md` (розділи 2, 3, 9), `SDD/templates/design.md`,
`SDD/<продукт>/README.md` і `SDD/<продукт>/system/*.md`.

## Крок 1. Що треба з'ясувати

1. Фіча — за номером задачі (`/sdd-code-check <N>`); гілка — за правилом «одна задача = одна
   гілка» (`CLAUDE.md`): перемкнись на `sdd/<N>-*` і онови її з `origin`. Знайди папку фічі
   `SDD/<продукт>/changes/<N>-*/`.
2. Збери список питань:
   - `proposal.md` → «Питання до розробки» (рядки без відповіді);
   - `spec.md` → маркери `[ПОТРЕБУЄ УТОЧНЕННЯ: …]` і «Припущення» без позначки ✅;
   - питання, які розробник додав сам;
   - **після Гейта 1 у повному режимі (підготовка до `/sdd-design`)** — питання виводь **сам** з
     правил `spec.md`: для кожного БП, що потребує коду, — що зараз є (дані, контракт, екран,
     права) і що доведеться змінити; плюс незлиті гілки за задачами фічі. Не питай розробника,
     «що досліджувати» — це твоя робота.
3. Покажи список одним повідомленням і досліджуй; розробник може додати своє, але відповідь
   для старту не потрібна.

## Крок 2. Доступ до коду — лише читання

1. У `SDD/<продукт>/README.md` → «Код» указано репозиторій і **гілку продукту**. Репозиторій
   може обслуговувати кілька продуктів окремими гілками — читай саме гілку продукту
   (наприклад, `release/shop`), а не ту, що зараз відкрита в розробника.
2. Спитай шлях до локального клону репозиторію коду (або візьми з попередньої відповіді).
3. Не змінюй робочу копію розробника: жодних `checkout`, `switch`, `commit` у ній.
   - `git -C <клон> fetch origin` — дозволено;
   - для читання файлів створи тимчасовий worktree:
     `git -C <клон> worktree add --detach <тимчасова-тека> origin/<гілка-продукту>`
     і читай файли там. На Windows тримай шлях коротким (наприклад, `C:/wt/<гілка>`) і додавай
     `-c core.longpaths=true` до `git worktree add`: у репозиторії бувають задовгі шляхи файлів.
     Наприкінці видали його:
     `git -C <клон> worktree remove <тимчасова-тека>`.
   - Якщо інструменти не мають доступу до теки поза репозиторієм специфікацій — попроси
     розробника виконати `/add-dir <тимчасова-тека>`.
4. Запиши, яку гілку й коміт читаєш (`git -C <клон> rev-parse --short origin/<гілка>`): ця
   позначка йде в кожну відповідь.

## Крок 3. Відповіді

Для кожного питання:

1. Знайди в коді, що відповідає (пошук за назвами полів, текстами інтерфейсу, типами документів,
   назвами таблиць). Читай достатньо, щоб відповідь була фактом, а не здогадкою.
2. Сформулюй **факт мовою бізнесу**: що бачить і може користувач, які є поля, статуси, ролі.
   Назви класів, таблиць, файлів — **не у факт**, а в колонку «Де в коді».
3. Познач надійність:
   - ✅ **підтверджено кодом**;
   - ⚠️ **частково** — код показує механізм, але результат залежить від даних / налаштувань;
   - ❓ **з коду не встановити** — що потрібно, щоб встановити.
4. Якщо факт **суперечить** proposal або spec (наприклад, поле не можна редагувати, документ
   завантажується в іншому місці), — запиши «Наслідок для proposal / spec» **з адресатом**:
   `ПМ ⏳: …` (межі, метрика, апетит) або `БА ⏳: …` (правила, тексти, ролі). Самі ці файли
   **не правиш**: це шар ПМ і БА.
   **Після Гейта 1** розбіжність наявного коду чи незлитої гілки зі spec — **не** наслідок для
   ПМ / БА, а робота розробки: запиши її як ТР «приводимо до spec» (конституція, розділ 7).

Не більше одного питання за раз показуй розробнику на підтвердження, якщо відповідь неочевидна;
очевидні — показуй пачкою наприкінці.

**Факти не пропонуються варіантами.** Не став питань про систему у вигляді «А (рекомендовано) /
Б / В» і не підказуй «правдоподібну» відповідь: це те саме вгадування, яке забороняє конституція,
а людина під тиском часу відповість «а». Якщо факт не знайдено в коді — постав **відкрите**
питання («що показує код / дані?») і познач ❓. Те саме — коли розробник відповідає сам, без коду
(зокрема в навчальних фічах): лише відкрите питання, без варіантів.

## Крок 4. Куди записувати

1. **`design.md` → «Факти про поточну систему»** (створи файл за шаблоном, якщо його немає —
   це шар розробки). Колонки: питання, факт, надійність, де в коді (`шлях:рядок`), гілка@коміт,
   дата, наслідок для proposal / spec.
2. **`proposal.md` → «Питання до розробки» → колонка «Відповідь розробки»** — одне коротке
   речення і посилання «див. design.md, Р-n». Інших частин proposal не змінюй.
3. **`spec.md` → «Припущення»** — лише колонку «Підтверджено»: ✅ / ❌ з посиланням на факт.
4. **`SDD/<продукт>/system/`** — факти, які діятимуть і для майбутніх фіч (ролі, статуси, поля
   профілю, типи документів, обмеження платформи). Кожен — із джерелом: задача, гілка@коміт,
   дата. Технічні деталі — у `platform.md` або в розділах «Для розробки».
5. Персональних даних з БД чи логів у файли не переноси — лише структуру й правила
   (конституція, розділ 9).

## Крок 5. Завершення

1. Видали тимчасовий worktree.
2. Підсумок для розробника: скільки ✅ / ⚠️ / ❓, які наслідки для proposal / spec, що
   переходить ПМ і БА.
3. Запропонуй:
   - «відправ на погодження» — коміт у гілку фічі (`sdd/<N>-…`), той самий MR (порядок — у `CLAUDE.md`);
   - якщо є `ПМ ⏳` / `БА ⏳` — коментар у MR **адресно** (кому, що вирішити, одним реченням
     кожне); текст — перед відправкою;
   - питання ❓ — на задачу з міткою «Питання до розробника» або «Питання до замовника».
4. Нових питань немає, а Гейт 1 пройдено в повному режимі — наступний крок розробки
   `/sdd-design <N>`, а не ПМ.

## Хто наступний

Наприкінці — **завжди** рядок «**Далі:** <хто> — `<команда>` (<що зробити>)» за
`SDD/checklists/next-step.md` (перше правило, що спрацювало). Не відповідай «у мене все» без
імені й команди наступного.
