# /sdd-design · як ми це зробимо

Ти допомагаєш **розробнику** описати, як фіча буде реалізована, — щоб розробка й тестування
пішли без сюрпризів, а БА міг звірити рішення зі spec. Пиши українською. Тут доречна
технічна мова: це шар розробки.

Перед початком прочитай: `CLAUDE.md`, `SDD/constitution.md` (розділи 2, 7, 9),
`SDD/checklists/next-step.md`, `SDD/templates/design.md`, папку фічі (`proposal.md`, `spec.md`,
`design.md` → «Факти»), `SDD/<продукт>/system/`.

## Крок 1. Чи можна починати

1. Фіча — за номером (`/sdd-design <N>`); гілка — за правилом «одна задача = одна гілка»
   (`CLAUDE.md`).
2. **Гейт 1 пройдено?** (`spec.md` у `main` або MR зі spec влито.) Якщо ні — скажи, що
   рішення можна чернеткою, але Гейт 2 — лише після Гейта 1, і хто зараз наступний за
   `next-step.md`.
3. Режим швидкий — `design.md` потрібен лише з «Фактами»; скажи це і не пиши зайвого.
4. Є «Питання до розробки» без відповіді чи маркери в spec — спершу `/sdd-code-check <N>`.

## Крок 2. Spec — правда

Після Гейта 1 `spec.md` — погоджена правда (конституція, розділ 7):
- **наявний код чи незлита гілка розходяться зі spec** — це робота: запиши ТР
  «приводимо <що> до БП-n» (наприклад, «гілку фронтенду беремо за основу, прибираємо рядок
  пошуку — не входить за proposal»). Питати ПМ / БА **не треба**;
- **розробник вважає, що spec неправа чи неможлива** — ТР «пропоную змінити БП-n: …» з
  причиною і «Звірено БА» ⬜. Рішення — за БА.

## Крок 3. Рішення — разом із розробником

Заповнюй розділи шаблону. **Факти — лише з коду** (якщо чогось не знаєш — подивись у коді або
`/sdd-code-check`); **рішення** — одне за раз, розробник обирає. Кожне рішення подавай
**одразу таблицею** — коротких варіантів у три рядки для технічного вибору замало:

| Варіант | Плюси | Мінуси | Ризик / що треба заміряти |
|---|---|---|---|

і під таблицею — рекомендація з причиною.

| Розділ | Що | Перевірка |
|---|---|---|
| **Рішення** | компоненти й потік даних, коротко; діаграма — якщо допомагає | кожна гілка рішення має причину (чому так, а не інакше) |
| **Контракти** | API сторінки й інтеграції: запит, відповідь, помилки, значення за замовчуванням, версія | **кожен параметр / поле → правило spec (БП-n)**; немає правила — або зайве, або бракує правила (ТР для БА). **Зворотна сумісність** — див. нижче |
| **Дані** | таблиці, поля, індекси, міграції, перенесення даних | обсяги: якщо рішення залежить від кількості записів — це замір у «Ризиках» (див. «Заміри») |
| **Налаштування без релізу** | ключі, значення за замовчуванням | кожне → правило spec |
| **Технічні рішення, що уточнюють spec** | ТР-n: рішення, правило, «Звірено БА» ⬜ | лише те, що **видно користувачу** або змінює правило; внутрішня кухня — у «Рішення» |
| **Ризики й заміри** | що може не вкластися (швидкодія, обсяг), як перевіримо | — |
| **Розбивка на задачі** | підзадачі в трекері (бекенд / фронтенд / міграція), посилання на наявні | кожне БП, що потребує коду, — у якійсь задачі |

**Зворотна сумісність — обов'язкова перевірка.** Для кожного зміненого контракту: що
отримає наявний клієнт (сторінка, інтеграція), який **не передає нових параметрів**? Відповідь
має бути «те саме, що й зараз» — інакше це зміна чинного процесу, і вона мусить бути прямо
записана в `proposal.md` → «Межі» (конституція, розділ 8). Значення за замовчуванням нових
параметрів обирай так, щоб старий виклик поводився як раніше (наприклад, `null` = «як зараз»),
а не так, як «зручно новому інтерфейсу». Рекомендацію, що змінює поведінку старого виклику, не
пропонуй без явної позначки «змінює поточну поведінку для: …».

**Заміри.** Коли рішення залежить від обсягів, швидкодії чи якості даних:
- **стейджинг / тестова БД** — можеш заміряти сам, лише читання, лише кількості й час, без
  персональних даних;
- **бойова БД — ніколи сам.** Підготуй запити **лише для читання** (з оцінкою навантаження й
  порадою, коли запускати) для людини з доступом; результати, які вона принесе, запиши в
  «Ризики й заміри» з датою;
- знайдений дефект даних (порожні, биті, без зв'язку записи) — окремий ризик з рішенням (ремонт,
  обхід або «приймаємо») і місцем у розбивці на задачі.

## Крок 4. Покриття spec

Пройди всі БП зі `spec.md` і склади коротку таблицю: БП → де реалізовано (контракт / дані /
фронтенд / не потребує коду). Непокриті — назви розробнику. Критерії приймання (КП) — ними
перевірятиме QA; якщо якийсь КП неможливо перевірити за цим рішенням — це ТР.

## Крок 5. Завершення

1. Розділ «Готовність · Гейт 2» — чесно відміть.
2. Підсумок: ключові рішення, скільки ТР чекають БА, ризики.
3. Запропонуй «відправ на погодження» (той самий MR фічі або новий — за правилами `CLAUDE.md`)
   і коментар у MR для БА з переліком ТР ⬜ (текст — перед відправкою).
4. **Далі** — за `SDD/checklists/next-step.md` (зазвичай: БА — `/sdd-ba <N>`, звірка ТР; потім
   ПМ — влити MR, Гейт 2).
